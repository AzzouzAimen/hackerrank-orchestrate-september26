# Development semantic contract coverage audit

This is an offline audit of the current extractor runtime, not a model run. `build_cases()` in `code/prototype/extraction_experiment.py` currently builds only five representative cases and several synthetic controls; none of the 14 v5 development users is built as a runtime case. `request_content()` sends only `case_id` plus selected `events`, `messages`, and `images`, followed by the JSON schema. It does not send `financial_profiles.csv`, home currency, requests, payment options, or an implicit full user history. Images are sent as image bytes when `image_paths` is populated. Only event rows explicitly selected by `build_cases()` are visible to the model.

## Empty-output risk

Yes. The current `score()` function compares a usable model bundle against `case["reference"]`; if a reference is represented as `{"facts": []}`, a usable empty bundle produces zero unmatched references and no failure. Thus the five context-only cases above could receive an undeserved pass if their empty `required_contract_facts` were converted directly into empty scoring references. A coverage-aware scorer must distinguish “no required facts because the input cannot express the meaning” from “the model correctly found no facts,” and must mark the former input-limited rather than correct.

## Smallest general fix

Do not change the seven-fact schema yet. First make the runtime case builder consume the frozen development manifest and include each selected message/image/linked event plus the minimal history rows needed for stream targeting. For meanings with no event or currency in the source evidence (user_04, user_10, user_12, user_18, user_23), either provide an explicit, source-backed stream context in the input envelope or mark the case input-limited. User18 additionally needs concrete transfer event IDs to emit the existing lifecycle fact; otherwise it remains contextual until the contract is deliberately widened. Update scoring only after this input-coverage decision is approved.
