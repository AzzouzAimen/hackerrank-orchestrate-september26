## Actual runtime boundary

`code/prototype/extraction_experiment.py:103` builds five representative cases and separate diagnostic cases from explicitly selected CSV rows. It does not consume the semantic split or annotation files. Of the 14 development users, only user16 has a corresponding representative runtime case. Reading a whole CSV inside the builder does not send the whole CSV to the model.

`request_content` sends case_id and the case's evidence dictionary (events, messages, images), followed by the generated schema. Image paths become base64 PNG image attachments. Event rows retain event IDs, category, description, currency, dates, direction, status and linked_event_id. Message rows retain their metadata and text; image metadata retains user/request/event links. There is no profile/home-currency field, all-user history, or explicit stream-selector catalog. The prompt requires supplied event IDs or a precise supplied stream selector; it does not establish a rule for synthesizing selectors for new message-only streams.

The original user16 input includes salary history event_1336, event_1343, event_1350, event_1357, event_1364 and outstanding event_1442, message_12 and image_02. `rent_history_experiment.arms` explicitly appends event_1337, event_1344, event_1351, event_1358, event_1365 and event_1371 in treatment. This input distinction remains material. `prototype/run.py` reads profiles and all user events for deterministic replay of reviewed facts; it does not pass that context to the extractor. `code/main.py` invokes that replay, not a development-benchmark inference runner.

## Why an empty output can pass undeservedly

`EvidenceBundle(facts=[])` is schema-valid. The annotation validator also permits any case's required_contract_facts to be empty; five current cases are empty. It does not evaluate a model output at all. Its printed success therefore establishes neither semantic completeness nor model accuracy. A future scorer that checks only these empty required lists would award a vacuous success while missing ended income, contingent bonus, pending payout, internal transfer and pending prize. No current development scorer exists, so this is a concrete reference-design risk, not a measured model pass rate. Empty raw response text and valid JSON with an empty facts array are different outcomes.

Other validator gaps: it never verifies history ownership/existence, checks selector currencies against messages and linked events but excludes history/images, uses a four-currency hardcoded list, and does not establish the semantic relationship between a currency and a target. Mere presence of EUR in salary text cannot validate a childcare currency. It also does not bind references to serialized runtime payloads. The prior v3 readiness claim is therefore unsupported.

## Smallest general fixes (recommendations only)

1. **Input fix first:** create one offline development input builder using explicit selected evidence/history IDs and image bytes, preserve its exact payload/hash, and supply reviewed precise stream descriptors with field provenance. Require the references to cite that payload. No full profile is necessary, and home currency must not silently become every stream's currency. This addresses user12/user04 and known payroll stream targeting without changing the seven fact types.
2. **Only for genuinely missing target information:** retain the seven types but consider an evidence-anchored unresolved target in FactBase, allowing a message's subject to be recorded without a fabricated currency/event. Permit nullable related_event_id for an unresolved lifecycle relationship with unresolved_fields explicitly populated. Consumers must treat such targets as unresolved and non-actionable. Do not relax currency validation globally or convert unresolved subjects into ledger events. This is the narrow general direction for user10/user18/user23 and potentially childcare; it requires a separate reviewed schema/consumer change, not performed here.
3. **Reference gating:** track required semantic meanings independently of available serializations. Mark missing target/input coverage as not scoreable, never zero required meanings with full success. Store actual alternative contract bundles per meaning and distinguish optional raw restatements. No scorer was implemented.

Conclusion: seven types cover most important meanings; current required target fields and missing benchmark input wiring prevent complete supported coverage. Keep assistant_draft and do not freeze the development references until input binding and the unresolved-target cases have been adjudicated.
